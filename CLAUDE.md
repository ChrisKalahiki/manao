# Manaʻo

References such as `legacy-77` identify pre-publication development tickets, not issues in this repository. The technical decisions are documented here; new issues belong to ChrisKalahiki/manao.

A central hub for a single user's day-to-day work: one dashboard (and one read-only MCP server for agents) showing todos, calendar events, running agents, health Measurements and other signals. This repo currently contains read-only Herdr, Brain-Dump Todos, Google Calendar, Google Health and paper-bot Adapters, the SQLite store, the hub process that connects them (`manao run`), its read-only HTTP API, the dashboard it serves beside the API, and a read-only MCP server (`manao mcp`). Everything else is on `docs/ROADMAP.md`. Vocabulary (Source, Item, Event, Health, Healthy, Stale, ...) is in `GLOSSARY.md`.

You are picking this up with no memory of the design conversation. The decisions below were made deliberately; do not reverse them without asking.

## Architecture (decided)

- A local SQLite store is the hub's memory. One adapter per source pulls data on its own cadence and emits normalized `HubItem`s and `HubEvent`s through an `ItemSink` (`src/core/types.ts`). Adding a source should mean adding one adapter, not touching the core; a new kind of data does touch it (Measurements added `ItemSink.writeMeasurements` and a store part).
- One hub process (`manao run`) runs every enabled Adapter and is the store's only writer; other processes open the store read-only (WAL). See `docs/adr/0001-single-writer-hub-process.md`. Because the hub owns the store, it hands each Adapter what its Source stored before at start (`start(sink, stored?)`, `StoredState`: its Items, the date of its latest Measurement and its newest Event of each kind); an Adapter that carries on from them takes them (the Calendar its Items until its first good read, Health the date it reads on from, paper-bot its Picks and Scan Events so no Event repeats), the others leave the parameter out.
- The store holds current Items only (full replace per Source and type; `updatedAt` kept when title, Status, Attention and data are unchanged), Events with store-assigned increasing ids, one Health row per Source, and Measurements (one row per Source, Metric and local date, written through the sink's `writeMeasurements`, which replaces the days written and keeps the rest; never pruned, and kept when their Source is removed, like Events). Schema versioned with `user_version` (2 added Measurements): the hub upgrades an older store in place through each part's `CREATE ... IF NOT EXISTS`, and a reader refuses one older than it reads until then. Health `error` and `note` are stored with paths under the home directory written `~/...` (`homeRelative`, `src/home-path.ts`), since Health crosses the tailnet; the CLI's startup lines, its errors and the sign-in's token line do the same.
- **Healthy rule:** a Source is Healthy when its latest Health report is ok and no older than that report's `staleAfterMs` (default 3x the refresh interval). Every queried Item carries `sourceOk` and `lastOkAt`, so Stale data never passes as current. No Health row means not Healthy.
- Config is one JSON file (`config.example.json`), validated by hand with errors naming the field; no file means Herdr with defaults. At startup the hub removes the Items and Health of Sources the config no longer enables (their Events stay), and prunes Events older than `eventRetentionDays` (default 30) at startup and daily.
- Everything else reads the store through one core API: the dashboard UI (a PWA made of independent widgets) and a read-only MCP server so agents can ask "what is on my plate" or "which agents need me".
- **The read-only HTTP API** (`src/api/`) runs inside the hub process and reads the hub's own store. Node's built-in `http`, no framework. Listens on `127.0.0.1` only (config `api.port`, default 7420; `api: false` turns it off); it starts after the store and Adapters, a taken port stops startup, and the hub's `stop()` closes it. GET only, no CORS, no authentication (the tailnet is the boundary). `/api` is JSON only; every other path serves the dashboard's static files (below). Every request passes the same guards in order: `Host` must be `localhost:<port>`, `127.0.0.1:<port>` or a `*.ts.net` name (403, against DNS rebinding), method GET (405), a known path (404), known and well-formed parameters (400 naming the parameter). Every error body is `{ error }`; every success body carries `now`, the hub's clock. Endpoints today: `GET /api/items?type&status&attention`, `GET /api/events?after&limit` or `?since`, `GET /api/sources`, `GET /api/agenda` (no parameters; spec: issue `legacy-59`), `GET /api/measurements?metric&from&to` (local dates, inclusive: `to` defaults to Today, `from` to `to` minus 6; from after to or a span over 366 days is a 400; spec: issue `legacy-66`). Spec: issue `legacy-16`. Phones reach it through `tailscale serve`, never `funnel`.
- **The dashboard** (`dashboard/`, spec: issue `legacy-39`) is a Preact + Vite app (dev dependencies only; its own `dashboard/tsconfig.json` with DOM lib and Preact JSX) that `bun run build` builds into `dist/dashboard/`. The API server serves it at every path outside `/api`, after the same Host (403) and GET (405) guards (`src/api/dashboard.ts`): files only from that folder (any `%`-escape, backslash or dot-led segment is a 404, and so is a symlink or anything whose real path leaves the folder's real path), types from a small extension map, page, manifest and service worker `no-cache`, `/assets/*` (content-hashed) immutable, a `'self'`-only CSP with `frame-ancestors 'none'`, nosniff and no-referrer on every dashboard reply, its 403, 405 and 404 included (`/api` replies carry none of them); errors stay `{ error }`. Not built: `/` is a 404 saying to run `bun run build`, logged once at startup, and `/api` still answers. The folder is the hub option `dashboardDir` (default `dist/dashboard` beside the built hub), which is how tests point it at fixtures. The dashboard reads only existing `/api` endpoints; each widget (`dashboard/src/widgets/`) takes its slice of the data plus the hub's `now`, the only clock for ages. Two views, switched by tabs in the masthead (links, no router) and addressed by the URL hash (`dashboard/src/view.ts`): **Today** (`#today`, and the home with no hash) renders the Agenda as the hub selected it, doing no selection of its own; three sections, always shown, in order: Needs you (`/api/agenda`'s `attention`, "Nothing needs you." when empty), Appointments (`appointments`: every `appointment` Item whose span overlaps Today, ended ones included, all-day first, then by start, then by title; overlap reads `data` as the Status rules do, timed instants against the start and end of Today in the system zone, all-day dates with Google's exclusive end, and an Item whose `data` is not in that shape is left out; rendered with the All view's Appointment rows, "Nothing on the calendar today." when empty) and Todos (`todos`: the open Todos nested as the Todos widget nests them, an open subtodo whose parent is ticked directly under its Todo Group, "No open Todos." when empty). **All** (`#all`) holds the six widgets below. One poller (`dashboard/src/poll.ts`) reads only what the visible view shows (Today `/api/agenda`; All `/api/items`, `/api/sources` and `/api/measurements` with its defaults) every 10s while the page is visible, reads at once when the view changes (clearing the previous view's failure), and keeps each view's last good read on screen when the hub is unreachable. Both views show a banner (hub unreachable, or which Sources are Stale: Today from the Agenda's `staleSources`); All then shows the Agents (what needs the user first), Appointments (the coming week by day: Today, Tomorrow, then weekdays, all-day first, then by start; a multi-day or overnight entry once, on Today while it runs, else on its first day; ongoing, Attention and ended marked in words; tentative and unanswered invitations labelled; out-of-office and focus time quiet; links only when `https:`), Todos (the Weekly Note's outline), Health (Measurements: one row per Metric, Steps, Sleep, Resting heart rate, Active zone minutes, then any other by id and unit; the latest value, sleep as "7h 12m", "so far today" for steps and active zone minutes on Today, "last night" for sleep, else "yesterday" or the weekday; over a 7-day SVG bar strip ending Today, scaled per Metric, a missing day no bar, a zero a sliver, each day's value as screen-reader text), Papers (the `paper` Items from the same `/api/items` read: this week's Picks by `date`, newest first, Today, Yesterday, then weekdays, paper-bot's order within a day; the title linked only when `https:`, Interests as tags, the why line, Wildcard and Kept in words; each day's heading links its Briefing as `obsidian://open?file=<vault-relative path>`, naming no vault since manao knows none and an absolute `path` differs per device, so Obsidian opens it in the vault it has open; "No Picks this week." when empty) and Sources (Health) widgets; each shares the `Widget` frame and marks Stale data as last known (`LastKnown`) rather than hiding it. Days are the hub's: Today is the date of the hub's `now`, timed Appointments' instants are grouped into days in the device's zone, which is assumed to be the hub's until the cross-cutting `timeZone` option (`docs/ROADMAP.md`) gives both one zone (all-day dates arrive already in the hub's zone). An invitation the user has not answered (`needsAction`) shows no Join, since anyone can send one whose video link points anywhere; its Google Calendar link stays. It installs as a PWA: `dashboard/public/` holds the manifest and icons (copied unhashed to the root, so `no-cache`); a hand-written service worker (`dashboard/sw/`, no PWA plugin or Workbox, its own WebWorker tsconfig) builds to `/sw.js` with scope `/`, and the build's own plugin (`dashboard/shell-plugin.ts`) writes that build's shell (the page, every emitted asset, the public files) and a version hashed from their contents into it. The worker precaches the shell under `manao-shell-<version>`, deletes older shells on activate, answers shell paths cache-first and never touches `/api` (no `respondWith`, no cache). The page registers it only in the production build.
- **The read-only MCP server** (`src/mcp/`, `manao mcp`) is a separate process an agent's client launches over stdio (ADR 0001); `@modelcontextprotocol/server` v2 with `zod` 4. stdout carries only protocol messages; logs go to stderr. No HTTP transport. It finds the store as the hub does (`resolveDbPath`, reading the config only for `dbPath`) and opens it read-only on the first tool call, retrying on every call until it opens; a missing store, a newer `user_version` or a refused open is a tool error naming the path, never a startup failure. Tools carry `readOnlyHint: true` and input and output schemas, and return `{ now, ... }` as structured content plus a text block that starts with a Stale warning naming each Source that is not Healthy, then the JSON. Tools today: `list_items`, `list_events`, `list_sources` and `agenda` (no parameters; the same query as `GET /api/agenda`, so it returns exactly what the Today view shows) and `list_measurements` (the same query as `GET /api/measurements`). Spec: issue `legacy-21`. Other machines run it over SSH on the hub host; no `.mcp.json` in the repo.
- **One query layer** (`src/query/`) holds every read's parameters and query; the API's routes and the MCP tools both call it, so their rules never drift. Each parameter carries its query-string reader and its zod schema side by side.
- The hub can run continuously on a private host. Other devices reach its PWA through Tailscale; it must not be exposed publicly.
- Language and stack: TypeScript, Node 22+, ESM, vitest. bun is the package manager and script runner; Node is the runtime. Use `bun run test`, never `bun test` (that is bun's own runner, not vitest). SQLite via `better-sqlite3` (v12; it has no prebuilt binary for Node 20, which is why the floor is 22, and v13 is now open), listed in `trustedDependencies` so bun runs its install script.

## Decisions and their reasons

- **Agents are read-only for now.** No terminal input, no focus, no writes to the vault or calendar. Writes may come later, but they need a permissions and audit design first.
- **Herdr agents** come through `sources.herdr`, on when the config has no `sources` (spec: issue `legacy-83`; `socketPath`, `intervalSeconds` 5, `events` true, `staleAfterSeconds` 3x interval). Source `herdr:local`: the herdr-core on the hub's own machine, named before the hub connects. Each refresh is one `terminal.list` (`src/herdr/types.ts` strips everything manao does not keep); every local terminal whose program reports a status is an `agent` Item keyed by its address, Status `running`, `needs_attention` (blocked or error; `data.statusLabel` is `error` for the latter), `finished`, `idle` or `unknown`, Attention on `needs_attention` and `finished`. A `done` older than 30 minutes by its `status_ms` on the hub's clock is `idle` (`FINISHED_ATTENTION_MS`): Codex leaves `done` when its terminal is viewed, Claude Code only at its next prompt, so a finished Claude Code agent would otherwise stay on the Agenda all day; ageing out is a `changed` to `idle` Event, never `completed`. `agent.transition` Events (`appeared`, `changed`, `cycled`, `gone`) come from comparing against the last stored read, `completed` when a change lands on `finished` or on `idle` with a higher `turn`; the Adapter takes a read as compared against only once its Items and Events are written. `events.subscribe` (`EventNudger`) only nudges a re-read; the 5s poll is the safety net.
- **The Obsidian vault is the source of truth for Todos, read through Brain-Dump.** The hub is a lens over it, not a second task system. The vault may sync across devices. Brain-Dump writes the Weekly Notes and owns their format, so the `brain-dump` adapter runs `brain-dump todos` and parses its JSON; it never parses the vault and never imports Brain-Dump's code (bun vs Node). It may watch the vault folder only as a hint to re-run the command. See ADR 0002. Do not couple the core to it: it is one adapter.
- **Brain-Dump Todos are opt-in** through `sources.brainDump`: `command` defaults to `brain-dump` (bare name on PATH, absolute path or `~/...`), `intervalSeconds` to 60, `staleAfterSeconds` to 3x interval. The Adapter runs `todos --date <Today>` using the hub's injected clock in the system zone, validates JSON, and emits `todo` Items with `open`/`done`/`dropped` Status and no Attention. It resolves the vault root through `<command> vault`, caching success and retrying on later reads while unresolved. A non-recursive Node `fs.watch` watches only the directory of the vault-relative `note` under that root and moves when the folder changes. Changes trigger coalesced `refresh()` after 2s of quiet (`debounceMs` is an Adapter option, not config); polling remains the safety net. Vault resolution or watch failures appear in Health `note` and are retried on later reads. `stop()` closes the watcher and clears poll and debounce timers. Todo read failures keep Items Stale; `exists: false` is a successful empty read. Under launchd both the executable and its bun interpreter must be resolvable.
- **paper-bot Picks are opt-in** through `sources.paperBot` (spec: issue `legacy-77`): `command` defaults to `paper-bot` (bare name on PATH, absolute path or `~/...`), `intervalSeconds` to 900, `staleAfterSeconds` to 3x interval. Like Brain-Dump, a CLI behind a JSON contract that paper-bot owns (ADR 0002's pattern; the contract is in `src/paper-bot/contract.ts`): the Adapter runs `picks --json` (10s timeout), validates it (`src/paper-bot/contract.ts`), and never writes to paper-bot or the vault. Source `paper-bot:picks`. Every good read replaces the Source's Items with the contract's `picks`, which are this week's as paper-bot reports them, so last week's drop out when the week rolls over; the hub trusts the contract on that and checks no Pick's `date` against `week`. Each Pick is a `paper` Item (`src/paper.ts`), id `paper-bot:<Paper id>`, Status `picked` or `kept`, `data` holding `title`, `url`, `date`, `interests`, `wildcard`, `why`, `briefing` and `keptAt`, never Attention, so never on the Agenda. Health after a good read is the pure `scanHealth` (`src/paper-bot/health.ts`) on the hub's clock: ok only when the Daily Scan exists, did not fail and its `at` is under 26 hours old, the Weekly Scan did not fail (none yet is fine), and `keeps.failing` is empty; each broken rule is named in `error`, and sources that failed in the Daily Scan are named in `note` without making it Unhealthy, also when the Daily Scan itself failed (the note then says which sources). A missing Daily Scan (`null`, before paper-bot's first) is not Healthy. A non-zero exit, a timeout, output that is not JSON or off the contract keeps the last Picks Stale with an error naming the cause (`commandErrorMessage`, shared with Brain-Dump). Events (pure, `src/paper-bot/events.ts`): `scan.daily` / `scan.weekly` (`scanEvents`) when that Scan's `at` differs from the last one recorded (`data`: `at`, `date` or `week`, `outcome`, `reason`), and `paper.kept` (`keptEvent`; `data`: Item `id`, `title`, `url`, `date`, `keptAt`) when a Pick is kept and its Keep is not recorded, a Pick first seen already kept included, but none while no Picks are known, so a new store does not replay old Keeps. A stored Item is `kept` only once its Keep Event is recorded, and a good read writes in this order (`PaperBotAdapter.write`): the Picks with the Keeps recorded so far, the new Scan Events, then for each new Keep its Event and then the Picks showing it, one Keep at a time. So at most the newest `paper.kept` Event is ahead of the stored Picks, and what the Adapter compares against starts from `stored` (`seenFromStored`: the Picks stored as kept plus the newest `paper.kept` Event's Pick, the newest `scan.*` Events' `at`): neither polling, a restart, nor a refused write followed by a restart loses or repeats a Keep. A refused write is not Healthy and retried on the next read; a Scan whose Event was pruned (`eventRetentionDays`) is recorded again once. Known gap: "no Picks are known" is also a restart whose stored week was empty, or the Source turned back on (its Items removed, its Events kept), so a Keep made while the hub was down then is not recorded; telling that apart from a new store would need every recorded Keep, not just the newest.
- **Google Calendar Appointments are opt-in** through `sources.googleCalendar` (spec: issue `legacy-49`): `calendars` defaults to `["primary"]`, `intervalSeconds` to 300, `daysAhead` to 7, `staleAfterSeconds` to 3x interval; it requires the top-level `google.client`, the path to the Desktop OAuth client JSON from Cloud Console, absolute or `~/...` like `dbPath`. No `.env`: launchd never reads one and a Desktop client's secret is not confidential. Source `google-calendar:primary` (one Adapter per Google account). The token lives at `$XDG_DATA_HOME/manao/google-token.json` (`resolveGoogleTokenPath`), mode 0600, written by `manao auth google` (below). `src/google/oauth.ts` is the account, shared with Health: plain `fetch` (no Google library), 10s per request, base URLs as options (`GoogleEndpoints`, how tests reach the fake; `createAdapters`' `AdapterEnvironment` passes them and `googleTimeoutMs`, never config); it reads the token file on every fetch, so a new sign-in needs no restart. The Health API refuses a token that also carries other APIs' scopes (issue `legacy-74`), so `accessToken(scopes)` never uses the sign-in's access token: it mints one narrowed to exactly the reader's scopes by a refresh grant with `scope`, kept in memory per sorted scope set while the file still holds the refresh token it came from and until a minute before expiry (a new sign-in's refresh token never reuses one). After each refresh it re-reads the file: if a sign-in wrote a new refresh token meanwhile, that one wins and the refresh is redone with it; otherwise the file is rewritten (atomically, temp file and rename, mode 0600) only when Google issued a new refresh token. It throws `GoogleError` with a `kind`: `not-connected` ("not connected: run `manao auth google`": no token, `invalid_grant`, a 401; an unreadable or corrupt token file names the file and cause, still ending in the sign-in to run), `missing-scope` (checked from the token's granted scopes before any request), `unreachable` (network, 5xx, "timed out after 10000ms"), `refused` (a calendar not found, forbidden, or configured twice, named; a 403 adds Google's reason code, never its message, which names the Cloud project), `client` and `unexpected`. Every configured id is resolved through `calendarList` before any events are read; two that are the same calendar (`primary` and its own id) fail the fetch naming both, refused rather than merged because Item ids carry the configured id. Scopes `calendar.calendarlist.readonly` and `calendar.events.readonly`. Each fetch reads `calendarList` (to resolve names and confirm each calendar exists), then `events.list` per calendar with `singleEvents=true`, `orderBy=startTime`, from the start of Today to the end of Today plus `daysAhead` in the system zone on the hub's clock, following `nextPageToken`, each with a `fields=` partial response naming only what the schemas keep (`attendees(self,responseStatus)`), so descriptions, attendee emails and dial-in PINs never leave Google; all or nothing, and any failure keeps the Items Stale. Declined, cancelled, `workingLocation` and `birthday` entries are left out. Items of type `appointment`, id `<calendar id>:<instance id>`; `data` holds `allDay`, `start`/`end` (ISO instants, or local dates with Google's exclusive end), location, calendar id and name, meeting link, the user's response, `eventType` and `htmlLink`, never the description, attendees or dial-ins (the response schemas drop them). Status and Attention are the pure `appointmentStatus` and `appointmentAttention` (`src/appointment.ts`, the Appointment's source-independent time model, which the query layer shares): Attention from 15 minutes before a timed Appointment starts until it ends, never for all-day, `outOfOffice` or `focusTime` entries. They are computed at fetch time and again by a 30s tick on the hub's clock, which recomputes the last stored Appointments and replaces them only when a Status or Attention changed (so `updatedAt` moves only on a real change); the tick never reports Health, so only a fetch makes the Source Healthy, and `stop()` clears it with the poll. A tick takes its Appointments as stored only once the write succeeds, so a refused write is retried. The tick starts from the store's last known Appointments (`stored`, dropped whole if any is not in this version's shape) and runs once right after the startup fetch, so a restart whose first fetch fails still moves Status and Attention on (no ended meeting left raising Attention). Appointments that ended earlier Today stay `ended` until the first fetch past midnight, whose window leaves them out.
- **`manao auth google`** (`src/google/sign-in.ts`, spec: issue `legacy-51`) is the one-time sign-in, run on the hub host or over SSH with `-L`. It reads `google.client` from the config and asks for the union of the enabled Google Sources' scopes (`googleScopes`: the Calendar's pair, Health's three), refusing to start when none is enabled; each Source then checks only its own, so a token missing Health's scopes fails only Health (`missing-scope`). It listens on `127.0.0.1` (a free port, or `--port`, which exists for an SSH forward set up before the port is known), prints the consent URL and opens it (an injected `openBrowser`; the CLI skips it when `SSH_CONNECTION` is set), and judges only a GET of `/` that carries `state` and whose `Host` is `127.0.0.1:<port>` or `localhost:<port>`; anything else is a 404 and the wait goes on, so another local process or a page cannot abort it. Then `state` is checked and the code exchanged with PKCE S256 (`access_type=offline`, `prompt=consent`, so a refresh token always returns). It writes the token through `writeToken` only when every requested scope was granted: a partial consent is refused and writes nothing. Any failure (wrong `state`, denied consent, an unticked scope, missing or malformed client file, taken port) names the cause, exits non-zero and writes nothing, so an earlier token keeps working. The browser gets a plain-text page saying which. The README's "Google connection" covers the Cloud Console setup.
- **Google Health Measurements are opt-in** through `sources.googleHealth` (spec: issue `legacy-66`, probe findings: issue `legacy-67`): `intervalSeconds` defaults to 3600, `backfillDays` to 30 (1 to 90), `staleAfterSeconds` to 3x interval; it requires `google.client`. Source `google-health:primary`, through the same `GoogleConnection` (`postJson` beside `getJson`, since a roll-up is a POST) against `health.googleapis.com/v4`. Four Metrics, read one after another, each request checking only its own scope, every one following `nextPageToken`: `steps` (count) and `active-zone-minutes` (minutes) from a `dailyRollUp` (`windowSizeDays: 1`, a CivilDateTime range whose end is exclusive; days as `civilStartTime.date`), active zone minutes being the plain sum of the fat-burn, cardio and peak sums, which Google already weights (cardio and peak count double; the probe checked); `resting-heart-rate` (bpm) from the `daily-resting-heart-rate` data points filtered on `daily_resting_heart_rate.date`; `sleep` (minutes) from the `sleep` data points filtered on `sleep.interval.civil_end_time`, whose response has no civil fields, so the hub takes the wake date as `endTime` plus `endUtcOffset` and sums `minutesAsleep` over every session ending on it, naps included (`nap`/`mainSleep` ignored). Dates in `{year,month,day}` are Google's civil days taken as given; values come as int64 strings, newest first, and a day with no data is left out, so it stores nothing (a reported zero is stored). Each refresh reads from the earlier of yesterday and the day after the latest stored Measurement through Today, at most `backfillDays` back (the backfill, two days normally, a catch-up after downtime); all or nothing, and any failure writes nothing and keeps the Source Stale. Any refused status keeps only the `google.rpc.ErrorInfo` reason code (capitals and underscores only), never Google's message: a 403 is `refused` ("steps: forbidden (REASON)"), a 429 `unreachable` ("steps: rate limited (REASON)"; the next poll retries), any other `unexpected` with the reason appended; `SERVICE_DISABLED` adds "enable the Google Health API in your Cloud project", as the Calendar's `accessNotConfigured` does, both through `forbidden` (`src/google/oauth.ts`). Measurements survive restarts and the Source being turned off; turned back on, it carries on from the latest stored day. Metrics and their units live in `src/measurement.ts` (`METRICS`); a Measurement never raises Attention or reaches the Agenda.
- **Health data uses the Google Health API, not the Fitbit Web API.** The legacy Fitbit Web API stopped support on 2026-09-30 and turns off on 2026-11-02 (Google's docs); OAuth tokens do not carry over; all Google Health API scopes are Restricted. Checked 2026-10-20 against Google's docs: a personal Cloud project needs no verification or CASA for one user, and Testing mode's refresh tokens expire after 7 days, so a personal deployment can use In production and remain unverified (one click-through warning). Lapsed tokens still happen (revoked, or unused for about 6 months), so the widget needs a visible "reconnect" state. The probe (issue `legacy-67`) confirmed the API scopes: steps and active zone minutes `activity_and_fitness.readonly`, sleep `sleep.readonly`, resting heart rate `health_metrics_and_measurements.readonly`. Health Connect cannot be read off the phone without an Android exporter, and is not needed for a Fitbit tracker.
- **Discord is bot-only.** Reading personal DMs or unread counts is not supported for normal accounts and user tokens violate Discord's terms. Do not build that.
- **Keep it shareable.** No hardcoded paths, tokens or usernames; configuration lives in a config file; secrets live in env or an untracked file, with an `.env.example`. Treat "which task source" and "which sources are enabled" as configuration.

## Hard rules

1. **Never add a method to `READ_ONLY_METHODS`** in `src/herdr/client.ts` beyond `hello`, `server.status`, `terminal.list`, `terminal.get` and `events.subscribe`. herdr-core's socket has no authentication and the same surface can type into terminals, run programs, write files and stop the core. Do not allow `terminal.read`, `terminal.attach`, `file.read` or `doc.get` either: they return screen text, files or opaque documents, which can contain secrets. Never store a terminal's `argv` or `foreground` (command lines).
2. **Never replace a source's items with an empty list because the source failed.** Report health instead (`ItemSink.reportHealth`). Stale and visible beats silently empty.
3. **Never trust an event payload.** Events are only hints to re-read authoritative state.
4. No secrets, tokens, or personal data in commits.

## herdr-core facts you will need

The Herdr app runs its terminals on herdr-core (`hc` 0.1.16). `hc --help` and `hc server status` are the reference; there are no published docs for the socket.

- JSON-RPC 2.0, one message per line, on a Unix socket at `$XDG_STATE_HOME/herdr-core/default/default.sock` (`~/.local/state/...`). `HC_TERMINAL_SOCKET` is set only inside herdr-core's own terminals, so the hub ignores it. `HC_SOCKET` (a socket path) and `HC_SESSION` (a core name, socket `<name>/<name>.sock`) move `hc` to another core; the Herdr app uses the default, so manao honours neither and `socketPath` covers the rare other case. `hc server status` starts the core it looks for if none runs, so never probe with it. Every connection starts with `hello` `{generation: 1}`; another generation is an error with `data.kind: "unsupported_generation"`.
- herdr-core deals in terminals (`t1`, `t2`, ...). `labels.where` is where the app shows one ("Manaʻo / 1"); the app sets it (with `herdr.space` and `herdr.tab`) on every terminal it opens, so only a terminal started with `hc run` outside the app lacks it. Terminals from another machine appear as `machine/t7`; the hub leaves them out.
- `status` is what the program reports about itself (OSC 7501), not inferred from the screen: `state` is `idle`, `working`, `done`, `blocked` or `error` (the program's own words, "nothing is translated": `error` is whatever the agent reports as one, so Attention is right for it), with `app`, `msg`, `kind` (why blocked) and `progress`. A shell reports none (`status: null`). `turn` goes up each time the status leaves `working`, into `blocked` too (Codex's permission prompts move it), which is how a finished cycle between two polls is seen; `completed` needs `finished`, or `idle` on a higher turn, so a block is never counted as one.
- `events.subscribe` acknowledges with `{channel, seq, terminals}`, then pushes `event` notifications (`{type, seq, terminal, data}`; every new status `msg` is its own `status` event), `heartbeat` every 15s and `missed` when the core dropped events. Types: created, lost, restarted, keep, finished, removed, status, turn, title, labels, size, doc. Measured over 4 minutes with two agents working: 1,676 `title` events (a working Codex retitles its terminal about every 100ms, about once a second when not), 6 `status`, 2 `turn`, 15 heartbeats; so the nudger ignores `title`, `size`, `doc` and `keep`.

## Verified against the real herdr-core

Verified against `hc` 0.1.16 (issue `legacy-87`): the hub under launchd reaches the default socket and `herdr:local` is Healthy (`herdr:default` removed at startup); Claude Code and Codex Items, Attention and `agent.transition` Events match what happened through working, a permission prompt (`needs_attention`, never `completed`), done and idle; the Agents widget and Today's "Needs you" render correctly in the mobile dashboard. Viewing a finished Codex terminal moves it `done` → `idle` on the same turn; a finished Claude Code agent stays `done` until its next prompt, hence the 30-minute limit above.
